# Сервис покупки товара

Микросервис на NestJS, который обрабатывает покупку товара на маркетплейсе: списывает деньги с покупателя, начисляет продавцу, переводит товар в статус SOLD и публикует событие о покупке в RabbitMQ

Ключевые гарантии: один товар покупает ровно один пользователь даже при 50 одновременных запросах, операция идемпотентна по ключу из заголовка, при падении на любом шаге система остаётся консистентной

## Стек

Node.js 22, NestJS 10, TypeScript (strict, без `any`), TypeORM, PostgreSQL 16, RabbitMQ 4, Vitest, Testcontainers, pino, prom-client, env-var

## API

Единственный бизнес-роут:

```
POST /purchases
Idempotency-Key: <ключ, уникальный в рамках покупателя>
X-Request-Id: <опционально, иначе сгенерируется>

{ "productId": "uuid", "buyerId": "uuid" }
```

Ответ 201 с телом покупки. Повторный запрос с тем же ключом возвращает то же тело и заголовок `Idempotent-Replay: true`

Авторизация не реализована сознательно: по условиям задания она не нужна, поэтому `buyerId` приходит в теле запроса

### Коды ошибок

Все ошибки имеют одинаковую форму: `statusCode`, `code`, `message`, `details`, `requestId`, `timestamp`, `path`

| Код | HTTP | Когда |
| --- | --- | --- |
| `VALIDATION_FAILED` | 400 | невалидное тело или лишние поля |
| `IDEMPOTENCY_KEY_REQUIRED` / `IDEMPOTENCY_KEY_INVALID` | 400 | нет заголовка или некорректная длина |
| `PRODUCT_NOT_FOUND` / `USER_NOT_FOUND` / `ACCOUNT_NOT_FOUND` | 404 | нет товара, покупателя или счёта в валюте товара |
| `PRODUCT_ALREADY_SOLD` | 409 | товар уже купили |
| `IDEMPOTENT_REQUEST_IN_PROGRESS` | 409 | защитный случай: закоммиченная заявка на ключ без результата |
| `INSUFFICIENT_FUNDS` | 422 | не хватает денег |
| `SELF_PURCHASE_FORBIDDEN` | 422 | продавец покупает свой товар |
| `UNSUPPORTED_CURRENCY` | 422 | валюта счёта не совпадает с валютой товара |

## Как реализована логика

Вся покупка выполняется в одной транзакции `READ COMMITTED`:

1. заявка на ключ идемпотентности: `INSERT ... ON CONFLICT DO NOTHING RETURNING id`
2. чтение товара с `SELECT ... FOR UPDATE`
3. блокировка счетов покупателя и продавца в детерминированном порядке `ORDER BY id`
4. проверка бизнес-правил и перевод денег в доменном слое
5. запись товара, балансов, покупки и двух проводок ledger
6. сохранение канонического результата в запись идемпотентности
7. добавление события `purchase.completed` в outbox

Событие в брокер отправляет отдельный воркер `OutboxRelay` уже после коммита

### Схема данных

Деньги не лежат полем в `users`, а разделены как в продакшене:

- `users` — пользователи
- `accounts` — баланс, `UNIQUE (user_id, currency)`, `CHECK (balance_minor >= 0)`
- `products` — товар, `CHECK (price_minor > 0)`, согласованность `status` и `sold_at`
- `purchases` — факт покупки, `UNIQUE (product_id)`, `CHECK (buyer_id <> seller_id)`
- `ledger_entries` — двойная запись DEBIT/CREDIT, `UNIQUE (purchase_id, account_id, direction)`
- `idempotency_keys` — `UNIQUE (user_id, idempotency_key)` и сохранённый результат в jsonb
- `outbox_messages` — события, частичный индекс по неопубликованным

Суммы хранятся в минорных единицах (копейки) в колонках `bigint`, в приложении это безопасные целые числа. Числа с плавающей точкой к деньгам не применяются нигде

## Инженерные решения

### Конкуренция за товар

Точка сериализации — `SELECT ... FOR UPDATE` по строке товара. 50 одновременных запросов встают в очередь на этой блокировке, первый переводит товар в SOLD, остальные видят его недоступным и получают 409

Полагаться только на код было бы недостаточно, поэтому есть второй рубеж на уровне БД: `UNIQUE (product_id)` в `purchases`. Нарушение этого ограничения репозиторий транслирует в доменную ошибку `ProductAlreadySoldError`, а не отдаёт наружу 500

### Идемпотентность

Ключ резервируется первым шагом транзакции через `ON CONFLICT DO NOTHING`. Если параллельный запрос с тем же ключом ещё не закоммитился, PostgreSQL блокирует вставку на уникальном индексе до конца его транзакции. Дальше два исхода: победитель закоммитился и мы отдаём его сохранённый результат, либо он откатился и мы честно выполняем операцию

Такая схема убирает необходимость в отдельном статусе `IN_PROGRESS`: строка становится видимой только вместе с результатом

Сознательные упрощения по условиям задания: TTL у ключей нет, сравнение хеша тела запроса не делается, кешируются только успешные ответы

Важное следствие: неудачная попытка не расходует ключ. Транзакция откатывается целиком, заявка на ключ исчезает, и повторный запрос с тем же ключом может завершиться успешно. Это проверено интеграционным тестом

### Гонки за балансом

Один покупатель может параллельно купить несколько товаров и уйти в минус. Поэтому счета покупателя и продавца блокируются `FOR UPDATE`, а инвариант закреплён `CHECK (balance_minor >= 0)` на уровне БД

Блокировки берутся в едином порядке: сначала товар, затем счета отсортированные по `id`. Без этого два пользователя, покупающие друг у друга одновременно, получали бы дедлок

Дополнительно на пул выставлен `lock_timeout`, чтобы запрос падал быстро, а не висел на блокировке бесконечно

### Консистентность и событие в RabbitMQ

Прямая публикация в брокер внутри транзакции создаёт классическую проблему двойной записи: событие ушло, транзакция откатилась, или наоборот. Поэтому реализован transactional outbox

Транзакция покупки только дописывает строку в `outbox_messages`. Воркер `OutboxRelay` выбирает пачку через `FOR UPDATE SKIP LOCKED`, публикует в topic exchange `marketplace.events` с publisher confirms и помечает строки опубликованными. `SKIP LOCKED` позволяет нескольким инстансам разгребать outbox параллельно

Доставка at-least-once: брокер может подтвердить сообщение, а транзакция после этого не закоммитится. Консьюмеру нужно дедуплицировать по `eventId`. Это осознанный trade-off в пользу того, что событие никогда не теряется

Контракт события:

```json
{
  "eventId": "uuid",
  "eventType": "purchase.completed",
  "eventVersion": 1,
  "occurredAt": "2026-08-18T10:15:30.123Z",
  "data": {
    "purchaseId": "uuid",
    "productId": "uuid",
    "buyerId": "uuid",
    "sellerId": "uuid",
    "amount": { "minorUnits": 150000, "currency": "RUB" },
    "purchasedAt": "2026-08-18T10:15:30.100Z"
  }
}
```

Недоступность RabbitMQ не мешает покупкам: события накапливаются в outbox, readiness при этом честно сообщает, что инстанс не готов

### Обработка ошибок

Доменные ошибки не знают про HTTP. Базовые классы описывают семантику (`NotFoundError`, `ConflictError`, `UnprocessableError`, `InvariantViolationError`), а маппинг в статусы живёт в единственном exception filter в presentation-слое

Ошибки драйвера PostgreSQL не протекают наружу: репозитории разбирают код ошибки и имя ограничения и превращают их в доменные ошибки. Имена ограничений вынесены в константы, общие для миграции и репозиториев

`InvariantViolationError` наружу отдаётся как 500 без деталей: это признак недостижимого состояния, а не пользовательская ошибка

### Архитектура

Разделение по слоям внутри модуля: `domain` (сущности, value objects, доменный сервис, ошибки, события, порты репозиториев), `application` (use case, команды, результаты, порты), `infrastructure` (TypeORM, мапперы, метрики), `presentation` (контроллер, DTO, swagger-декораторы)

Доменный слой не зависит от NestJS, HTTP и TypeORM. Вся бизнес-логика покупки собрана в `PurchaseSettlementService`, поэтому её можно тестировать без инфраструктуры

Транзакция прокидывается через порт `TransactionManagerPort` и async local storage (`nestjs-cls`): use case объявляет границу транзакции, но ничего не знает про `EntityManager`, а репозитории сами подхватывают активную транзакцию

`process.env` читается ровно в одном месте — config-слое. Дальше всё получают типизированные конфиг-объекты через DI

Переменные окружения читаются и валидируются через `env-var` прямо в фабриках конфигов — один файл на секцию, без промежуточных схем и типов:

```ts
export const databaseConfig = registerAs('databaseConfig', () => ({
  url: get('DATABASE_URL').required().asUrlString(),
  poolSize: get('DATABASE_POOL_SIZE').default(10).asIntPositive(),
  statementTimeoutMs: get('DATABASE_STATEMENT_TIMEOUT_MS').default(5_000).asIntPositive(),
  lockTimeoutMs: get('DATABASE_LOCK_TIMEOUT_MS').default(3_000).asIntPositive(),
}));
```

Типы секций выводятся из фабрик, отдельные интерфейсы не нужны: потребители инжектят `ConfigType<typeof databaseConfig>`. Фабрики выполняются при регистрации `ConfigModule`, поэтому отсутствующая или битая переменная валит старт приложения, а не первый запрос

### Observability и runtime

- `x-request-id` реализован через `ClsModule.forRoot` с `middleware.mount = true`, `generateId = true` и `idGenerator`, который берёт заголовок или генерирует uuid
- логирование pino умеренное: старт, shutdown, завершённые покупки, 5xx. Access-лог отключён, наблюдаемость HTTP закрыта метриками
- метрики: `http_requests_total`, `http_request_duration_seconds`, `http_requests_in_flight`, `purchases_total{result,reason}`, метрики outbox, дефолтные метрики процесса
- `/readyz` проверяет PostgreSQL и RabbitMQ и начинает отдавать 503 на `beforeApplicationShutdown`, до фактического закрытия сервера
- `/livez` проверяет только p99 задержки event loop: недоступность БД не должна приводить к рестарту здорового процесса
- graceful shutdown дожидается текущей пачки outbox, закрывает канал и соединение RabbitMQ и пул PostgreSQL. В образе используется `dumb-init`, чтобы SIGTERM доходил до Node

### Как устроены unit-тесты

Живут рядом с кодом как `*.spec.ts`, инфраструктуру не поднимают, работают на подставных реализациях портов

Покрывают value object `Money` (минорные единицы, отрицательные суммы, несовпадение валют), доменный сервис `PurchaseSettlementService` (перевод денег, двойная запись, уже проданный товар, покупка своего товара, нехватка средств, ровно нулевой остаток, чужая валюта) и `CreatePurchaseUseCase` (единственная транзакция, порядок шагов, запись в outbox, реплей по ключу, бизнес-метрики, все негативные сценарии)

### Как устроены интеграционные тесты

`test/integration/setup/global-setup.ts` один раз на весь прогон поднимает через Testcontainers реальные PostgreSQL и RabbitMQ и передаёт адреса в воркер. `env-setup.ts` заполняет окружение до импорта приложения, `test-app.ts` собирает настоящее Nest-приложение с теми же pipes, interceptors и filters, что в продакшене, и применяет миграции

Suite'ы выполняются последовательно, перед каждым тестом таблицы очищаются через TRUNCATE. Фабрики в `test/integration/factories` создают покупателя, продавца и товар

Мокирования нет принципиально: проверяемое поведение (`FOR UPDATE`, `ON CONFLICT DO NOTHING`, `SKIP LOCKED`, CHECK-ограничения, уникальные индексы) существует только в реальной БД

Покрыты все роуты:

- `POST /purchases` — happy path с проверкой балансов, статуса товара, проводок и outbox; реплей по ключу; 10 параллельных запросов с одним ключом дают одну покупку; 20 одновременных покупателей на один товар дают ровно один 201 и 19 конфликтов; параллельные покупки одним покупателем не уводят баланс в минус; нехватка средств; покупка своего товара; повторная покупка проданного товара; неизвестный товар, покупатель, счёт; отсутствующий и слишком короткий ключ идемпотентности; невалидное тело и лишние поля; форма ошибки и проброс `x-request-id`; неудачная попытка не расходует ключ
- `GET /livez` и `GET /readyz` — статусы и состав проверок, а также отсутствие `/health`
- `GET /metrics` — формат Prometheus, бизнес-метрики созданной и отклонённой покупки, label маршрута по шаблону
- outbox relay — публикация в RabbitMQ и чтение события из очереди, отметка `published_at`, отсутствие повторной публикации, отсутствие второго события при реплее

Request id в тестах генерируется через `uuid`, статические значения не используются
